Start issue: $ARGUMENTS

Treat all arguments as user-provided context, not authorization. Operator first reads repository instructions and project context, then shared `MEMORY.md`, before asking which tracker to use. Reuse a remembered tracker only when project memory explicitly marks that selection as remembered; ask GitHub/Jira only if that choice is missing or conflicting. Never write memory automatically. Confirm the issue key/URL, repository identity and safety context, and the human's identity in the selected tracker before acting. Clarify ambiguity; for example, `#96` alone is not enough to identify a GitHub repository, so never guess. GitHub work must not require Jira configuration or access. External verifies that the issue is assigned to the confirmed human before research or planning; never guess identity or proceed unassigned.

Before any worktree is created, Operator inspects the canonical checkout read-only. `<base>` is the project's configured base branch (`baseBranch` in project context); if it is missing or ambiguous, Operator asks Lead. If the checkout is dirty (any staged, unstaged, or untracked change, as `git status` reports), mid-operation (a merge, rebase, cherry-pick, revert, or similar operation in progress), not on the base branch, or detached, Operator reports the observed state and waits for explicit human confirmation; it never repairs the checkout. Otherwise Lead relays the step to External with `<base>` and the canonical checkout path. External runs `git fetch`, then checks read-only (for example, `git rev-list --left-right --count <base>...origin/<base>`) whether local `<base>` is ahead of or diverged from `origin/<base>`; if it is, External reports and waits for the human, with no repair. Otherwise External runs `git merge --ff-only origin/<base>`; if the fast-forward is not possible, External reports and waits. Then Operator inspects repository instructions, base branch, existing worktrees and unrelated changes, and prepares an isolated task worktree from the updated base. If Operator's shell tool is not offered, or the worktree command is denied or its permission prompt is declined, Operator creates nothing and reports the exact outcome. Lead stops bootstrap with Needs your decision and presents the fallback: the human creates the task worktree from the updated base (for example `git worktree add -b <branch> <worktreeDirectory>/<name> <base>`) and reports its path, or cancels. Lead does not route local Git to another role, broaden permissions, or retry automatically. Preserve existing worktrees and unrelated changes; do not overwrite, reuse, or clean them up as a shortcut. Read `worktreeDirectory` and `memoryPath` from project context and do not ask about valid values; ask only on missing, invalid or conflicting settings, collisions, or unsafe state. Never search the workspace for `MEMORY.md` or create one there. External reads the issue and linked parent when present. Apply only lifecycle mappings explicitly confirmed for this project: do not invent GitHub `In Progress` or `In Review` states. An absent optional mapping does not block; an explicitly required but unresolved transition does. Stop when required access or context is uncertain.

Use only the explicitly selected design source. Ask if required context is missing or conflicting; do not silently fall back or combine sources. Nonvisual work does not require a design service. Once requirements are clear, Lead defaults to inline inspection and scoping for understood low-risk tasks, or Researcher inspects relevant code and Planner prepares scope, implementation approach and checks when delegation is justified. File count never decides delegation; a delegated Implementer owns code, tests, and documentation together for a behavior unit. Reuse an adequate smoke plan or draft one; manual smoke is default, automation may be proposed. Include prerequisites, steps and expected outcomes. Standardize turn status reporting around Working, Checking, Ready, and Needs your decision. Lead presents the plan and smoke plan and waits for explicit conversational human approval before implementation; arguments never supply approval. Implement only the approved scope. Reviewer/QA perform applicable checks and report findings; obtain individual or clearly batched accept/discard decisions before fixing, and fix only accepted findings. Lead gets final human approval before any push or PR; External publishes only afterward. Never merge. Before cleanup, evaluate candidate memory learnings once for approved consolidation into `AGENTS.md`; approve the resulting diff before publication, rejecting secrets and operational paths. Human confirmation of merge triggers External verification and authorizes safe Operator cleanup; preserve remote branches and stop on dirty, unpushed or uncertain state.

On interruption or context loss, preserve existing local and remote state untouched. Operator inspects local Git/worktree and External inspects remote/service state read-only; Lead presents the resume checklist, marks missing approvals unconfirmed, and waits for explicit human confirmation before resuming. On uncertain external or local mutations (such as push, PR/issue creation, transition, comment, or cleanup), inspect actual state read-only: record verified completion without repeating the write, or report incomplete/diverged/inconclusive state and wait for human confirmation before retrying.
