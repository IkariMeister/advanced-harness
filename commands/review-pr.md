Review pull request: $ARGUMENTS

Treat command arguments as opaque context, not approval; do not tokenize or recursively substitute the full input. Confirm repository and PR identity; ask if ambiguous. External reads PR and linked Jira/parent context when available. Reviewer examines the diff and existing PR checks first. Propose further local checks to the human; do not automatically run isolated checks.

Assign the highest applicable review risk tier, explain why, and escalate uncertainty. Tiers guide review depth only: they do not waive scope, acceptance-criteria, consistency, or evidence checks, or authorize tools/actions. Low is localized, demonstrably behavior-preserving and reversible: zero specialized lenses plus the ordinary checks. Medium is a bounded behavior/workflow-instruction change without authority changes: one or two justified lenses. High includes approval, permission, ownership, security, material lifecycle, concurrency, persistence, recovery, or broad-contract hazards: all four lenses. For issue #61, expect medium Risk+Reliability unless a boundary change is found; stop for material scope change and renewed approval. Lens criteria: Risk—security/regressions, state effects and dependencies; Resilience—failure/retry/offline/cancellation/nullability/recreation; Readability—architecture/naming/idiomatic maintainability; Reliability—deterministic correctness, state ownership, complete tests, flakiness/races. For Compose, map Resilience to unsafe repeated effects/lost state on recreation and Reliability to state reads/effect keys/placement, stale state, loops, duplicate work. For Roborazzi, Reliability checks actual expected diffs/configuration and Resilience checks configured relevant error/loading/recreation; never silently accept baselines. For coroutines, Resilience checks lifecycle cancellation/cleanup and Reliability checks structured concurrency, scope/collector ownership, stale results/races.

Lead presents a structured summary (target/head, scope, tier/rationale, lenses and exclusions, uncertainty, acceptance criteria, existing checks, findings, and run/failed/blocked/unrun/waived checks with limits and next action) and concrete proposed feedback before posting. Findings have stable ID, lens, severity, location, observed issue, impact, evidence, proposed fix, and verification status; disposition remains pending until the human accepts/discards. Ask the human to choose exactly one disposition: Approve, Just Comment, or Request changes; suggest Request changes only for critical issues requiring a fix. Post only after explicit approval of concrete feedback and disposition. External posts approved feedback inline on relevant code lines. No source edits happen automatically; fixes require a separate approved implementation workflow.

On interruption or uncertain posting, preserve existing state untouched and inspect actual PR comments/reviews read-only through External: record verified posted feedback without duplicating comments, or report observed state to Lead and wait for explicit human confirmation before retrying.
